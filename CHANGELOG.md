# Changelog

All notable changes to AgentCordon are documented in this file.

## [Unreleased]

## [0.4.0] - 2026-09-07

### Added

- **Cutting a release is one command.** `release.toml` configures cargo-release: `cargo release <version> --execute` from a clean `main` bumps `[workspace.package] version` (which all five crates inherit and every binary prints), inserts a `## [<version>] - <date>` section under an untouched `[Unreleased]`, re-points the compare links, commits as `chore: release v<version>`, tags `v<version>` and pushes. Nothing is built or uploaded from a laptop, and no version string is typed twice. (`release.toml`, `docs/releasing.md`)
- **A pushed tag drives the whole release.** `.github/workflows/release.yml` triggers on `v*` tags (`workflow_dispatch` takes a tag for re-runs): `verify` refuses to build unless the tag equals the Cargo workspace version and `CHANGELOG.md` has a section for it; `build` produces the five-target binary matrix with signed build-provenance attestations; `release` assembles one `SHA256SUMS`, cuts the release body from that CHANGELOG section and marks `-rc`/`-beta`/`-alpha` tags as pre-releases; `container` pushes a multi-arch `linux/amd64,linux/arm64` image to `ghcr.io/agentcordon/agentcordon` tagged `<version>`, `<major>.<minor>`, `latest` (stable only) and `sha-<short>`, with OCI labels, SBOM and provenance; `smoke` pulls the published image and CLI, checks both report the release version, and fetches `/install.sh` from a started container to confirm it points at this tag. (`.github/workflows/release.yml`)
- **CI gates dependencies on advisories and licences.** `deny.toml` drives `cargo deny check advisories licenses bans sources` on every push and pull request; vendored asset licences (Inter, OFL-1.1; Lucide, ISC) are recorded in `THIRD_PARTY_NOTICES.md`. `scripts/check-version.sh` asserts that all three binaries print the workspace version; CI runs it on every push and the release workflow runs it with `--tag` before a single binary is built. (`deny.toml`, `scripts/check-version.sh`, `.github/workflows/ci.yml`)
- **The project's domain vocabulary and its architectural decisions are written down.** `CONTEXT.md` at the repository root is the glossary as the code uses it today: 69 terms across the three tiers, workspace identity and enrollment, credentials and vending, vaults, authorization, MCP, upstream OAuth, keys, the guards and audit, each naming the file it lives in and, where they differ, the word the console or the CLI uses instead. `docs/adr/` records the twelve decisions this release made, one file each, from deleting the PostgreSQL backend to deferring the authorization-model rework, with an index, a reading order and the interim rules the deferred rework leaves in force. Both are linked from `docs/index.md`. (`CONTEXT.md`, `docs/adr/`)

### Security

- **The last enabled Cedar policy can no longer be deleted or disabled.** Either left the install answering 403 to every operator, viewer and workspace, with only the root bypass still working and the policies page claiming a built-in default was in force; the seed only re-runs at boot, so it was not recoverable from the console. The seeded `default` policy refuses deletion outright; it stays editable, and disablable once another policy is enabled. The per-credential `grant:`/`deny:` rows do not count as "another policy". The empty state now says nothing is permitted except root. (`crates/server/src/services/policies.rs`)
- **Sharing a vault is the owner's act at any role, and only the owner's.** `manage_vaults`, an admin grant, no longer implies the right to grant a share, which would have let any admin hand out another user's credentials; it now reads any vault's share list and revokes any share, which is what auditing a share needs. (`crates/server/src/services/vaults.rs`)
- **Placing or moving a credential into a vault requires owning that vault (or root);** naming a vault no longer creates one, so a user can no longer join a vault by inventing its name and reach what its owner shares onward. (`crates/server/src/services/credentials.rs`)
- **A `read` share makes the vault's credentials visible to the recipient in the credential list and detail only.** It does not reveal secrets, grant to a workspace, or carry the right to re-share. Until now a share was stored and consulted by nothing. (`crates/server/src/routes/admin_api/credentials/list.rs`)
- **Managing an OAuth provider client requires the new `manage_oauth_provider_clients` Cedar action**, which the default policy grants to enabled admins only. Creating, editing, deleting and re-registering one was guarded by `manage_mcp_servers`, so any operator could rewrite or remove the registration every other tenant's MCP servers at that origin authenticate with. Listing stays on `manage_mcp_servers` (an operator still sees which client an origin uses, never its secret) and dynamic client registration during an MCP install is unaffected. The Settings page shows the listing to operators and offers the add, edit, toggle, re-register and delete controls to admins only. (`crates/server/src/services/identity_providers.rs`, `policies/default.cedar`)
- **A vault's share list is readable only by those who may change it.** `GET /api/v1/vaults/{name}/shares` required only `list` on `System`, so any signed-in user, a viewer included, could see who a vault was shared with and the user ids of the sharer and every recipient. The read is now gated per vault in the vault service exactly as sharing and unsharing are: the caller must own a credential in the vault or hold `manage_vaults` (admins, and root by bypass). Vault policy decisions also now name the vault in their audit row and carry the request's correlation id. (`crates/server/src/services/vaults.rs`)
- **An MCP server can no longer echo its own credential back to the agent.** Tool results and discovery probes were returned verbatim while only the proxy route scanned for leaks, so an upstream that mirrored its `Authorization` header or API key handed the raw token to the caller. The broker now runs the same `LeakScanner` over every MCP result and probe response, free text and nested JSON alike, replacing any injected value with `[REDACTED]`. (`crates/broker/src/routes/mcp.rs`)
- **Passphrase master secrets are stretched with Argon2id.** `AGTCRDN_MASTER_SECRET` fed HKDF directly, so a human-chosen secret produced an encryption key exactly as guessable as the passphrase. A secret carrying at least 32 bytes of material at 4+ bits of Shannon entropy per byte (64+ hex chars, base64 of 32+ bytes, or 32+ raw characters) is still used directly; anything weaker is stretched with Argon2id and a random 16-byte salt persisted at `<db dir>/.master-salt` (mode 0600, created once, never rotated automatically). Upgrades are safe: stretching only applies when the salt file already exists or the store is fresh, so an existing install with a weak secret keeps its key and gets a startup warning naming the rotation fix instead. The auto-generated `.secret` file is now 32 random bytes in hex. (`crates/core/src/crypto/master_secret.rs`)
- **Argon2 cost is a runtime setting, not a cargo feature.** The `test-crypto` feature weakened password and secret hashing at compile time, and cargo's feature unification could switch it on for a production build. It is gone; `AGTCRDN_ARGON2_M_COST_KIB`, `AGTCRDN_ARGON2_T_COST`, and `AGTCRDN_ARGON2_P_COST` (defaults 65536 / 3 / 4) carry the cost, the server installs them at startup, and the test harness installs cheap ones. An invalid value stops startup rather than silently lowering cost. (`crates/core/src/crypto/mod.rs`)
- **A second server on the same database is refused.** Two processes over one SQLite file each kept their own policy cache, rate limiters, and SSE bus, so they enforced different pictures of the world and both migrated the database. Startup now takes an advisory `flock` on `<db path>.lock` before migrations and holds it for the process lifetime; a second instance exits with a message naming the lock file and the escape hatch. In-memory databases are exempt, and `AGTCRDN_REPLICA_MODE=unsafe-shared` skips the guard. (`crates/server/src/config.rs`)
- **The broker terminates TLS itself.** `--tls-cert`/`--tls-key` were validated and then rejected at startup, so an operator had to put a reverse proxy in front of every non-loopback bind. The broker now serves HTTPS on its bind address with rustls (HTTP/1.1 and HTTP/2, graceful shutdown unchanged); without the flags it serves plaintext exactly as before, and `--shared-secret` remains an equally valid way to satisfy the non-loopback bind guard. Unusable material (unreadable file, no CERTIFICATE block, mismatched pair) stops the broker before the data directory is created, naming the flag at fault. (`crates/broker/src/tls.rs`, `crates/broker/src/daemon.rs`)
- **`AGTCRDN_BROKER_CA` tells the CLI which broker certificate to trust.** A broker serving its own certificate was unreachable from the CLI and the failure looked like "broker not running". Every certificate in the PEM file named by the variable is an extra trust anchor for the broker connection (verification is never disabled), and an untrusted broker is refused with a message naming the variable. The broker key pin is unchanged. A TLS broker must be reached via `AGTCRDN_BROKER_URL=https://...`; the local port-file discovery still assumes plaintext. (`crates/cli/src/broker.rs`)
- **Signed CLI requests carry a nonce; replays are refused.** The CLI-to-broker payload was replayable for 30 seconds. It is now `METHOD\nPATH\nTIMESTAMP\nNONCE\nBODY` with a fresh 16-byte `X-AC-Nonce`; the broker keeps a bounded seen-set of `(key, nonce)` for the skew window and answers a second presentation with 401. The `/register` body likewise signs `NAME\nPK\nSCOPES\nTIMESTAMP\nNONCE` and gets the same window and seen-set. Identity test vectors are re-frozen; CLI and broker must upgrade together. (`crates/identity/src/request.rs`, `crates/identity/src/register.rs`, `crates/broker/src/auth.rs`, `crates/broker/src/routes/register.rs`)
- **The broker publishes its key; the CLI pins it.** `GET /health` returns `encryption_public_key` and `key_fingerprint`; `agentcordon register` writes `.agentcordon/broker.fingerprint` (0600) and every later connection refuses a broker whose fingerprint differs, naming both values; `register --force` re-pins and pre-existing workspaces are pinned on first use with a notice. `AGTCRDN_BROKER_URL` is accepted only for loopback or `https://` and is refused before any request. (`crates/broker/src/routes/health.rs`, `crates/cli/src/pin.rs`, `crates/cli/src/broker.rs`)
- **Non-loopback broker bind requires a shared secret or TLS.** `--bind 0.0.0.0` used to expose the signed API to the network; the broker now exits at startup unless `--shared-secret`/`AGTCRDN_BROKER_SHARED_SECRET` or `--tls-cert`/`--tls-key` is set. With a secret, every route except `/health` requires `X-AgentCordon-Broker-Secret` (constant-time compare) and the CLI sends it from the same variable. TLS flags are validated but termination is not yet wired; the broker says so instead of serving plaintext. (`crates/broker/src/config.rs`, `crates/broker/src/daemon.rs`, `crates/broker/src/auth.rs`)
- **One broker per data directory; owner-only artifacts; single-flight refresh.** A second broker on the same `--data-dir` exits with a clear error (advisory `flock` on `broker.lock`); the data directory is 0700 and key, token store, port, pid, and lock files are created 0600 at open rather than chmod'ed afterwards. Two requests that both hit a 401 used to spend the refresh token twice; a per-workspace mutex re-reads state before refreshing, so concurrent 401s produce one token-endpoint call. (`crates/broker/src/daemon.rs`, `crates/broker/src/token_store.rs`, `crates/broker/src/token_refresh.rs`)
- **Brokers no longer hold provider secrets.** MCP sync shipped the upstream OAuth refresh token and the provider's client secret inside the credential envelope so the broker could refresh on its own; a compromised user machine exposed both. The server now runs the `refresh_token` and `client_credentials` exchanges itself through the shared `OAuth2TokenManager` and seals only the short-lived access token with its `expires_at`. A rotated refresh token is persisted on the server with a history row and a `CredentialSecretRotated` audit event. A sync entry whose exchange failed carries a `credential_error` string and no envelope; the rest of the sync still lands. (`crates/server/src/upstream_token_service.rs`, `crates/server/src/routes/control_plane/workspace_sync.rs`, `crates/core/src/oauth2/token_manager.rs`)
- **Vend exchanges client-credentials apps on the server.** `POST /api/v1/credentials/vend-device/{name}` for an `oauth2_client_credentials` credential vended the client secret plus token-endpoint metadata for the broker to exchange; it now vends the exchanged access token and its expiry, and the broker injects it as a bearer. (`crates/server/src/routes/admin_api/credentials/vend.rs`, `crates/broker/src/routes/proxy.rs`)
- **The broker never calls a token endpoint.** Its refresh manager, rotation callback, and client-credentials manager are gone. A cached upstream token is refreshed by syncing again when it is within 60s of expiry, and an upstream MCP 401 triggers one re-sync and one retry. `POST /api/v1/workspaces/mcp/rotate-refresh-token` is removed, so brokers and servers must be upgraded together. (`crates/broker/src/routes/mcp.rs`, `crates/broker/src/state.rs`, `crates/server/src/routes/control_plane/mod.rs`)
- **Master-secret rotation no longer loses every credential.** The documented runbook (change the secret, restart, call rotate-key) left the server with only the new key, so nothing could be decrypted. The encryptor is now a versioned key ring: `AGTCRDN_MASTER_KEY_VERSION` names the current secret and `AGTCRDN_PREVIOUS_MASTER_SECRET` loads the secret it replaces for the rollover window; the server refuses to start if the two are equal. (`crates/core/src/crypto/key_ring.rs`, `crates/server/src/config.rs`)
- **`key_version` records which master key sealed a row.** It was a re-encryption counter. New credentials, secret updates, refresh-token rotations, and history archives stamp the current version; decrypt selects that key, falling back across the ring for rows written before this release. Restoring a history entry restores its version too. Migration 019 rebuilds `credential_secret_history` so the column exists on every install and backfills it to 1. (`crates/server/src/credential_service.rs`, `crates/server/src/routes/admin_api/credentials/history.rs`, `migrations/019_secret_history_key_version.sql`)
- **`POST /api/v1/admin/rotate-key` re-seals history as well as credentials.** Each row is opened with the key its version names and written back under the current version; the response adds `key_version`, `history_re_encrypted_count`, and `total_history_entries`. Once it reports no errors the previous secret can be removed. `docs/master-key.md` describes the set-bump-restart-rotate-remove-restart procedure. (`crates/server/src/routes/admin_api/admin.rs`, `docs/master-key.md`)
- **The broker's vend is bound to its target.** The broker vended a credential without saying where it was going, so the server could not check the credential's allowed URL pattern. The vend request now carries `method` and `target_url`; a target outside the pattern is refused by the server before any secret leaves it. (`crates/broker/src/server_client.rs`, `crates/broker/src/routes/proxy.rs`)
- **The broker checks the pattern again before injecting, and fails closed.** The vend response carries `allowed_url_pattern`; the broker re-checks the target against it in the process that will inject, and refuses with 403 `forbidden` when it does not match or when a non-`generic` credential arrives with no pattern at all. (`crates/broker/src/routes/proxy.rs`)
- **Proxied and MCP calls use a dedicated outbound client.** Redirects were followed, which would carry the injected credential to wherever the upstream pointed; hop-by-hop headers were forwarded; responses were buffered without bound. The new client never follows a 3xx (the status and headers go back to the CLI), times out, caps the response at 10 MiB (over the cap is 502), and strips hop-by-hop headers in both directions. Response headers are returned as `[name, value]` pairs so repeated headers survive with their order; the CLI parses the list. (`crates/broker/src/upstream.rs`, `crates/broker/src/routes/proxy.rs`, `crates/broker/src/routes/mcp.rs`, `crates/cli/src/commands/proxy.rs`)
- **Request bodies are sent verbatim.** A JSON body was parsed and re-serialised, reordering keys and dropping whitespace, which breaks signed or hashed payloads. The body is now forwarded byte for byte under the caller's Content-Type (a body with no Content-Type is still labelled `application/json`). (`crates/broker/src/routes/proxy.rs`)
- **Injected secrets are redacted from upstream responses.** An upstream that echoed its request handed the credential straight back to the caller. Every injected header and query value, and the raw credential material, is now searched for in the response body and every response header in raw, base64, URL-safe base64, and percent-encoded forms, and replaced with `[REDACTED]`. (`crates/core/src/proxy/leak_scanner.rs`, `crates/broker/src/routes/proxy.rs`)
- **The broker's cached-scope pre-check is gone.** The broker refused proxy, credential, and MCP calls from its own stale copy of the token scopes, duplicating a decision the server makes from the token it issued. Scope enforcement now happens only at the server; a workspace whose cached scopes are out of date gets the server's answer instead of a local 403. (`crates/broker/src/routes/helpers.rs`, `crates/broker/src/routes/proxy.rs`, `crates/broker/src/routes/credentials.rs`, `crates/broker/src/routes/mcp.rs`)
- **SSRF check covers the full reserved address set.** The proxy and MCP guard only knew loopback, RFC 1918, link-local, and CGNAT; a target in 0/8, 192.0.0/24, 198.18/15, the TEST-NETs, multicast, 240/4, NAT64 `64:ff9b::/96`, 6to4 `2002::/16`, site-local `fec0::/10`, IPv6 multicast, or IPv4-compatible `::/96` was let through. One range function over `IpAddr` now rejects all of them, unwrapping mapped, NAT64, and 6to4 forms to apply the IPv4 rules; `localhost` and any `*.localhost` name are refused before DNS. A caller sees the same 400 `ssrf_blocked` it already got for loopback. (`crates/core/src/proxy/url_safety.rs`)
- **Sync-only SSRF variant removed.** `validate_proxy_target` checked only the URL text, so a hostname resolving to a private address passed; the admin tool-discovery route used it. Every caller now uses `validate_proxy_target_resolved`, which resolves the host and refuses if any returned address is reserved. (`crates/core/src/proxy/url_safety.rs`, `crates/server/src/routes/admin_api/mcp_servers/discover.rs`)
- **MCP tool-list probes are SSRF-checked.** The broker's live `tools/list` probe sent the injected credential to the cached upstream URL with no address check at all; only `mcp/call` was guarded. Probes now pass the same resolving check as tool calls, gated by `--proxy-allow-loopback` exactly as `/proxy` is; a server on a private or reserved address makes `POST /mcp/list-tools` return 400 `ssrf_blocked` naming the server, and the upstream receives nothing. (`crates/broker/src/routes/mcp.rs`)
- **Upstream MCP tokens are cached per workspace.** OAuth2 access tokens exchanged for an MCP server were cached by server name alone, so a second workspace bound to a same-named server received the first workspace's token. Caches are now keyed by workspace key hash and server id; each workspace's probe and call carries the token minted from its own refresh token or client secret. (`crates/broker/src/routes/mcp.rs`)
- **OIDC logins are bound to the identity provider's subject, not to a username claim.** The callback resolved the local account by whatever username claim the provider was configured to send, so any identity-provider account with `preferred_username` equal to `root` (or any admin's username) logged in as that user. A new `user_oidc_identities` table (migration 014) records `(provider, subject) → user`; logins resolve through it. On a subject's first login: if the resolved username is free, an account is provisioned and linked (when `auto_provision` is on); if it belongs to an unprivileged local account with no link, that account is adopted and linked, so viewers and operators provisioned before this change keep working; if it belongs to root or an admin, the login is refused and audited as `privileged_username_match`. The claim fallthrough (`preferred_username` → `email` → `sub`) is gone: a token missing the configured claim is refused rather than named after another claim. (`crates/server/src/routes/admin_api/oidc_auth/callback.rs`, `migrations/014_user_oidc_identities.sql`)
- **Revoking a workspace now revokes its access.** The workspace extractor rejected only `enabled = false` and never looked at `status`, and the revoke routes set `status = revoked` without touching tokens, so a revoked workspace's 15-minute access token and 30-day rotating refresh token kept working. Revocation now also disables the workspace, revokes its OAuth client, and revokes every access and refresh token issued to it; the extractor rejects any workspace that is not `active`. The two duplicate bearer validators are one function. (`crates/server/src/extractors/oauth.rs`, `crates/server/src/routes/control_plane/workspace_identity/management.rs`)
- **The workspace-identity routes require the manage-workspaces permission.** `GET /api/v1/workspace-identities`, the two revoke routes, and approve accepted any signed-in session, letting a viewer enumerate every workspace's key hash, revoke other tenants' workspaces, or approve a pending one and become its owner. They now run the same Cedar check as the device-flow approve route.
- **The browser consent flow can no longer be used to take over a workspace.** `GET`/`POST /api/v1/oauth/authorize` with `is_new_workspace` created a workspace and OAuth client for any caller-supplied key hash, gated only on having a session. It deleted the hash's existing client, reused the existing workspace row, and forced it back to `enabled`/`active`, so any signed-in user could hijack, reactivate, or knock offline any workspace whose key hash they knew (and the workspace-identity list handed those out). Both handlers now require the manage-workspaces permission, the same gate as the device-flow approve route. Re-registering an existing key hash is refused when the workspace is revoked or disabled (revocation is final; register a new identity), and when the caller is neither the workspace's owner nor an admin. Re-registration no longer changes lifecycle state at all. (`crates/server/src/routes/oauth/authorize.rs`, `crates/server/src/routes/oauth/consent.rs`)
- **Refresh-token reuse is detected and the family is revoked.** Rotation retired the presented refresh token with a compare-and-swap whose result was discarded, so two concurrent presentations of the same token both received fresh token pairs, and presenting an already-rotated token returned `invalid_grant` while its successor stayed valid. Refresh tokens now carry a `family_id` (migration 015; existing rows become the root of their own family) that rotation propagates. Presenting a retired token revokes every refresh and access token in its family and writes an `oauth_refresh_token_reuse_detected` audit event; the rotation itself now fails with `invalid_grant` when the compare-and-swap reports the token was already used. (`crates/server/src/routes/oauth/token.rs`, `migrations/015_refresh_token_families.sql`)
- **A Cedar policy that errors during evaluation now denies.** Cedar skips a policy that fails to evaluate and decides from the rest, so a `forbid` referencing a misspelled attribute silently stopped forbidding; the engine reported `Permit` with a non-empty error list that nothing read. A permit accompanied by any evaluation error is now returned as `Forbid` with reason `evaluation_error`, logged at warn. (`crates/core/src/policy/cedar/mod.rs`)
- **Audit exports are tenant-scoped and safe to open in a spreadsheet.** The CSV, syslog, and JSONL exporters built their filter without the user scope the list endpoint applies, so any user with view-audit (viewers and operators by default) could export every tenant's events, metadata included. The three exporters now apply the same rule as the list: non-admins get only their own events. The CSV escaper also prefixes any cell beginning with `=`, `+`, `-`, `@`, tab, or carriage return with an apostrophe, so a workspace or credential named `=HYPERLINK(...)` no longer executes when the export is opened. (`crates/server/src/routes/admin_api/audit/`)
- **The device-code token exchange binds the token to the approved key hash, not to a workspace name.** After approval, the exchange looked the workspace up by `workspace_name_prefill`; names are not unique, so two workspaces sharing a name could receive each other's client and grants. The exchange now resolves by `pk_hash_prefill` and falls back to the name only for device codes issued before the hash was recorded. (`crates/server/src/routes/oauth/token.rs`)
- **Approving a device code cannot re-bind another user's workspace.** Both approve paths (`POST /api/v1/oauth/device/approve` and the `/activate` form) approved the code first and only then discovered, while provisioning, that the key hash already belonged to a workspace the approver may not touch. A refusal at that point left an approved code with no workspace and answered 500. The re-registration rule from the consent flow (owner or admin only; never for a revoked or disabled workspace) is now checked before the row flips, and a refusal answers 403. (`crates/server/src/routes/oauth/device.rs`, `crates/server/src/routes/admin_ui/pages/activate.rs`)
- **A credential cannot be placed in another user's vault.** Create and update wrote the `vault` field straight from the body, so any user could move a credential into a vault they had no part in. Because owning one credential in a vault is what authorizes sharing that vault, this let a user share another user's vault with anyone. A vault may now be chosen when it is `default`, when it does not exist yet, or when it already holds a credential the caller owns; root may use any vault. Other choices answer 403. Workspace callers never join an existing vault. (`crates/server/src/routes/admin_api/credentials/`)
- **Transform settings are validated when they are saved.** `transform_name` was accepted unchecked and `transform_script` was only size-checked, so a typo or a script that does not parse surfaced as a proxy failure at first use. Both create and update now refuse a name outside the built-in set (`identity`, `basic-auth`, `bearer`, `aws-sigv4`) and a script the engine cannot compile, with a 400 that names the problem. An empty name or script on update clears the column. (`crates/core/src/transform/rhai_engine.rs`, `crates/core/src/storage/shared.rs`)
- **Policies are validated against the schema when the engine starts.** The add and replace routes validated in strict mode, but the constructor used at startup only parsed, so a policy seeded or edited directly in the database that named an unknown entity type or attribute loaded quietly and then failed at evaluation. The constructor now runs the same strict validation and refuses to start on a failure. That check found a dead statement in the shipped default policy: the admin-user permit on `McpServer` resources matched no schema action (MCP servers are managed through `System`), and it is removed. `policies/mock-tag.cedar`, which referenced a nonexistent `AgentCordon::Agent` type, is deleted. A core test loads every shipped `policies/*.cedar` file, so CI refuses a policy file that does not validate. (`crates/core/src/policy/cedar/mod.rs`, `policies/`)
- **Device-code issuance is rate-limited.** `POST /oauth/device/code` is unauthenticated and writes a row per call, so one source could fill the table and mint user codes for approvers to mis-approve. It now allows 30 requests per minute per (source address, `client_id`) and answers the rest with 429 `slow_down` and a `Retry-After`. The address follows the same rule as the other limiters (peer address; forwarded header only when `AGTCRDN_TRUST_FORWARDED_HEADERS=true`). (`crates/server/src/routes/oauth/device.rs`, `crates/server/src/middleware/sliding_window.rs`)
- **The activation page shows the device key and warns when it is already registered.** The approver saw only the workspace name the broker asked for, which is not unique and not bound to anything. The page now shows the key hash the code will bind, and when that key already belongs to a workspace it names that workspace and says approval re-registers it instead of creating a new one. (`crates/server/src/routes/admin_ui/pages/activate.rs`, `crates/server/templates/pages/activate.html`)
- **Bearer tokens are bound to their workspace by id.** A token reached its workspace by three lookups: token to client, client to public-key hash, hash to workspace. The hash is a property of the key, so a rotated or re-registered key silently re-pointed or orphaned every existing token. Migration 016 adds `workspace_id` to OAuth clients, access tokens, and refresh tokens, backfilled through the hash each row was issued against. New clients are created bound, tokens inherit the binding at issue time, a client registered ahead of its workspace is bound when the device flow provisions it, and the bearer extractor resolves token, client, and workspace in one store call. A client whose hash matched no workspace stays unbound and cannot authenticate, as before. (`migrations/016_oauth_workspace_id.sql`, `crates/core/src/storage/sqlite/oauth.rs`, `crates/server/src/extractors/oauth.rs`)

(`crates/server/src/install_script.sh`)
- **The generated `AGENTS.md` no longer breaks the agent's own broker connection.** It gave `AGTCRDN_BROKER_URL` a default of `http://localhost:3141`; the broker's default port is `0`, so it auto-selects and records the URL in `~/.agentcordon/broker.port`. An agent that believed the table and exported the variable lost every command. The file now says discovery is automatic, names the variable as an override only, adds a rule for choosing among MCP servers (match the task's service, prefer the server whose auth identity fits the question, never pick an unauthenticated server for an identity question), and tells the agent to run `agentcordon mcp-tools --schema` instead of guessing argument names. (`crates/cli/src/commands/init.rs`)
- **The API-key credential types are creatable from the admin UI.** `api_key_header` and `api_key_query` were accepted by `POST /api/v1/credentials` but the New Credential form offered three types and no way to supply the metadata the broker names the header or query parameter with, so both were reachable only by hand-crafting a request. The type select now offers them, a header-name field appears for one and a parameter-name field for the other, the value is submitted as `metadata.header_name` / `metadata.param_name`, and an empty name is refused before the request with the same sentence the API answers. Credential types are also labelled rather than echoed raw in the detail pill. (`crates/server/templates/pages/credentials/new.html`)
- **An MCP server can be disabled again.** `PUT /api/v1/mcp-servers/{id}` accepted only `name` and rejected any other field, so the admin UI's Enabled toggle failed with 422 and the documented immediate-revocation path, together with Cedar's forbid on disabled servers, could never fire. The update body now takes `enabled`, the change is audited on `McpServerUpdated`, and a disabled server drops out of broker sync and has its tool calls refused. (`crates/server/src/routes/admin_api/mcp_servers/mod.rs`, `crates/server/src/services/mcp_servers.rs`)
- **The documented API-key credential types work end to end.** `api_key_header` and `api_key_query` were rejected by `KNOWN_CREDENTIAL_TYPES` even though the docs and the broker's injection code both shipped them, and the sealed envelope carried only the secret, so the broker could never learn which header or parameter to use. Both types are now creatable (each requiring its `metadata.header_name` / `metadata.param_name`), their secrets are stored verbatim, and the envelope carries the credential's metadata, so an MCP server or API that wants `X-API-Key: <key>` or `?api_key=<key>` is reachable through the documented path. (`crates/server/src/services/credentials.rs`, `crates/server/src/crypto_helpers.rs`)
- **Audit event deep links expand again.** `/audit/{id}` left no row expanded and silently reverted the address bar to `/audit`: Alpine 3 runs a component's own `init()` and also evaluates `x-init`, so the audit page's `init()` ran twice and its second `toggleEvent(id)` closed the row it had just opened. The redundant `x-init="init()"` is dropped from every page and partial that carried it (17 in all), so a pasted event link opens that event and keeps its URL. (`crates/server/templates/pages/audit.html`)
- **Workspaces can be revoked from the admin UI.** Revocation, which is final and the only way to invalidate a workspace's OAuth clients and every access and refresh token, was reachable only by hand-crafting an authenticated `POST /api/v1/workspaces/{id}/revoke`; the detail page offered just Disable and Delete. Both workspace detail surfaces now carry a Revoke button behind a confirmation that spells out that it is final and that registering a new identity is the way back, Enable is refused once revoked, and the status pill reads Revoked instead of Disabled. (`crates/server/templates/partials/workspace_detail_pane.html`)
- **Master-key re-seal is a button in Settings.** Step 4 of the rotation runbook (`POST /api/v1/admin/rotate-key`) had no control anywhere in the admin UI, so an admin had to hand-roll a request with a session cookie and a matching CSRF token. Settings gains an admin-only Master Key card: Re-seal credentials, a confirmation, and a report showing the key version, credentials and history entries re-sealed against their totals, and any errors, which are the numbers the runbook says to check. (`crates/server/templates/pages/settings.html`)
- **The upstream OAuth2 token cache actually caches.** `OAuth2TokenManager` held a bare `DashMap`, whose `Clone` deep-copies every shard; since `AppState` and the services holding the manager are cloned per request, each request got a private cache it wrote once and dropped, so every credential vend and every MCP sync re-ran the exchange at the provider's token endpoint and rotated a delegated credential's refresh token on every sync tick. The map now lives behind an `Arc`, so clones share it: two vends or two syncs inside a token's lifetime make one round trip. (`crates/core/src/oauth2/token_manager.rs`)
- **A vend refused by `allowed_url_pattern` is audited.** The target check returned before Cedar ran, and Cedar is what self-audits denials, so a URL-pattern refusal wrote no audit row while a policy refusal did. The vend path now emits a `credential_vend_denied` event naming the workspace, the credential, the target URL and method, and the pattern it was checked against, before returning the 403. (`crates/server/src/services/credentials.rs`)
- **Discovered MCP tools keep their description and input schema.** `McpTool` deserialised `input_schema` while `tools/list` sends the spec's `inputSchema`, so every discovered schema was silently dropped, and the MCP detail endpoint rebuilt its tool list from `allowed_tools` with no descriptions. `McpTool` now reads the camelCase form through a serde alias (still emitting `input_schema` on AgentCordon's own wire), and the detail endpoint reports `discovered_tools`, falling back to bare names only when nothing was discovered, so `GET /api/v1/mcp-servers/{id}` and `agentcordon mcp-tools` show what a tool does and what arguments it takes. (`crates/core/src/domain/mcp.rs`, `crates/server/src/routes/admin_api/mcp_servers/`)
- **OAuth2 MCP discovery accepts an authorization server on another origin.** RFC 9728 protected-resource metadata exists so an MCP server can name an authorization server it does not host, but discovery required every discovered endpoint to be same-origin with the resource and refused that arrangement; the `WWW-Authenticate: Bearer resource_metadata="..."` hint on the MCP server's own 401 was never parsed. The origin lock now sits where it protects something: the authorization server's `issuer` must identify the URL its metadata came from (RFC 8414), every endpoint it advertises must be same-origin with that issuer, and each URL discovery fetches passes the resolving SSRF guard, while the authorization server may live anywhere. A template with no `oauth2_resource_url` is discovered by probing its MCP endpoint and following the `resource_metadata` challenge. (`crates/server/src/oauth_discovery/client.rs`, `crates/server/src/oauth_discovery/metadata.rs`)
- **SQLite errors are mapped in one place.** Unique, primary-key, and foreign-key violations came back as `Database(...)` from most store methods and reached clients as 500. One mapping now turns them into `Conflict` (with SQLite's constraint name) and a missing row into `NotFound`, so every route answers 409/404 consistently; sharing a vault twice or re-registering a revoked client's key hash now returns 409. (`crates/core/src/storage/sqlite/helpers/errors.rs`)
- **Timestamps use one fixed-precision format.** Rows were written with `to_rfc3339()`, whose fractional digits vary, so `ORDER BY created_at` could misorder rows within a second. All writes now use RFC 3339 with six fractional digits and `Z`; reads still accept the older values, and ordering is chronological across old and new rows. (`crates/core/src/domain/time.rs`)
- **Multi-step writes are single transactions.** The token endpoint consumed a device code or auth code and then inserted tokens separately, so a failed insert burned the code; secret rotation, restore, and upstream refresh wrote the history row and the new ciphertext separately, leaving an orphan history row on failure; consent re-registration deleted the old OAuth client before inserting the new one. Each is now one immediate transaction: a second concurrent exchange still loses and mints nothing, a failed mint leaves the code usable for a retry, rotation archives the ciphertext the row actually holds, and a failed client insert keeps the old client and its tokens. (`crates/core/src/storage/sqlite/device_codes.rs`, `crates/core/src/storage/sqlite/oauth.rs`, `crates/core/src/storage/sqlite/credentials/mod.rs`)
- **AWS SigV4 signs temporary credentials.** A credential JSON with `session_token` (or `aws_session_token`) was silently ignored, so STS and assumed-role keys were rejected upstream. The signer now sends and signs `x-amz-security-token`; callers see it in `SignedHeaders` and the injected headers. (`crates/core/src/transform/builtins/aws_sigv4.rs`)
- **AWS SigV4 double-encodes paths for non-S3 services.** Every service got the S3 single-encoded canonical URI, so any path segment with a space, `+`, or other reserved character signed wrong for Lambda, API Gateway, and the rest. Non-S3 services now encode each segment twice; S3-family services keep single encoding. Query strings are encoded once, sorted by key then value, with `=` kept for empty values. (`crates/core/src/transform/builtins/aws_sigv4.rs`)
- **AWS SigV4 reproduces the published test vectors.** Caller headers were never signed and `x-amz-content-sha256` was always added, so the signer could not match AWS's own worked example or test suite. Caller headers are now canonicalised and signed (hop-by-hop and client-rewritten headers excluded), and `x-amz-content-sha256` is added only for S3-family services. The AWS documentation IAM `ListUsers` example and eight `aws-sig-v4-test-suite` vectors pass byte-for-byte. Non-S3 callers no longer receive an `x-amz-content-sha256` header. (`crates/core/src/transform/builtins/aws_sigv4.rs`)
- **Policy audit no longer spawns an OS thread and blocks the async runtime on every Cedar evaluation.** `Authz::emit_audit` bridged into the store with `std::thread::scope` plus `Handle::block_on`, and list pages called it once per item, so a viewer loading a dashboard with a few hundred credentials spawned a few hundred threads and blocking database writes per page view. Emission is now a plain `.await`. `Authz::filter` writes one `policy_evaluated` row per call, whose metadata records how many items were evaluated, permitted, and denied and their ids (capped at 200 per outcome), instead of one row per item. The blocking `check_with_reasons_blocking` is gone; the stats endpoint, dashboard page, and policy tester now await the seam. (`crates/server/src/authz/mod.rs`)
- **Upgrading from v0.3.2 no longer deletes every MCP↔workspace binding.** Migration 012 rebuilt `mcp_servers` with `DROP TABLE` while foreign-key enforcement was on, so the junction table's `ON DELETE CASCADE` emptied `mcp_server_workspaces` on every upgrade. Brokers then synced zero MCP servers and workspace tokens lost their MCP scopes. The migration runner now recognises a `-- migration-mode: foreign_keys_off` marker on a migration's first line and runs that migration with enforcement off, inside one transaction, with a `foreign_key_check` before commit and enforcement restored afterwards (SQLite's documented table-rebuild procedure). 012 carries the marker. New migration 013 restores bindings on installs that already ran the cascading 012, by re-running the 010 backfill from the legacy `mcp_servers.workspace_id` anchor; bindings added via share after 010 cannot be recovered and must be re-created. (`crates/core/src/storage/migrations.rs`, `migrations/012_relax_mcp_servers_workspace_id.sql`, `migrations/013_restore_mcp_server_workspace_bindings.sql`)

- **Upgrading a pre-v0.3.0 database with duplicate credential names no longer fails at startup.** Migration 007 created a global unique index on `credentials.name`; credential names are not unique by design and 011 dropped the index again, but any database that reached 007 with two same-named credentials could not start. 007 is now a no-op (version 7 stays recorded). `scripts/migration-007-precheck.sh` is removed and the pre-upgrade checklist no longer asks for it. (`migrations/007_credential_name_unique.sql`, `docs/upgrading.md`)

- **`agentcordon init` no longer writes an `.mcp.json` entry for a command that does not exist.** Every init inserted `{"command":"agentcordon","args":["mcp-serve"]}`, and there is no `mcp-serve` subcommand, so Claude Code failed to start an MCP server on every session in an initialised workspace. `init` now leaves `.mcp.json` alone; MCP tools are reached through the broker via `agentcordon mcp-tools` and `agentcordon mcp-call`, as the generated instruction files already said. - **The from-source Dockerfile builds again.** It copied `crates/gateway/Cargo.toml`, a crate that was split into `broker` and `cli` in v0.3.0, so `docker compose -f docker-compose.build.yml up --build` failed at the first `COPY`. ## [0.3.2] - 2026-05-17

### Added

- **MCP servers can now be shared across multiple workspaces owned by the same user.** New `POST /api/v1/mcp-servers/{id}/workspaces` (body `{ workspace_ids: [UUID] }`, 201 on any added, 200 on all already-bound, idempotent on re-add; 403 for non-owner callers *and* for cross-user bind attempts where a target workspace's owner differs from the MCP's `created_by_user` — admin/root bypass this cross-owner check; 404 for unknown MCP or a workspace that does not exist; 422 on empty array). New `DELETE /api/v1/mcp-servers/{id}/workspaces/{workspace_id}` (204 on success; 403 for non-owner; 404 for unknown MCP or unknown binding; **409 Conflict** with `{"error":{"code":"conflict","message":"cannot remove last workspace binding — delete the MCP server instead"}}` when removing the deletion would leave the MCP with zero bindings — applies to admins too, the rule is a state invariant). The MCP detail page in the web UI has a new **Share with workspace** action — a modal with a multi-select of the owner's other workspaces — plus a per-row ✕ to unshare. New audit events `McpServerSharedWithWorkspace` and `McpServerUnsharedFromWorkspace` (one event per newly-created or -removed row; idempotent re-add emits zero events; the 409 last-binding rejection emits no state-change event). Unshare is eventually consistent: the target workspace's broker keeps the MCP cached until its next `mcp_sync` tick (~30 s) — for immediate revocation, disable or delete the MCP. Backed by a new `mcp_server_workspaces(mcp_server_id, workspace_id, created_at, created_by_user)` junction table with `ON DELETE CASCADE` from both parents; existing 1:1 `mcp_servers.workspace_id` records are backfilled into the junction by migration 010, and `mcp_servers.workspace_id` becomes an immutable audit anchor (never mutated by share, unshare, or removing the original workspace's binding).

### Changed

- **`agentcordon register` is now the one canonical workspace-registration command.** When you pass `--server-url <url>` (or set `AGTCRDN_SERVER_URL`) and no broker is running, `register` auto-starts a local broker pointed at that server before kicking off the RFC 8628 device code flow — matching the old `agentcordon setup` UX. Use `agentcordon init && agentcordon register --server-url <url>` for first-time onboarding.
- Error messages for "workspace needs re-registration" now point users at `agentcordon register --force` instead of the removed `agentcordon setup` command.
- **`GET /api/v1/mcp-servers/{id}` response's `installed_workspaces`** now lists every workspace bound to the MCP via the new junction table (was previously always a 0-or-1-element vec derived from `mcp_servers.workspace_id`). `mcp_servers.workspace_id` is kept as a legacy "original provisioning workspace" field for audit history; routing and authorization queries now go through the junction.
- **`GET /api/v1/mcp-servers?workspace_id=…`** joins through the junction so an MCP bound to multiple workspaces appears in each of their listings. `device_id` is accepted as a legacy alias.
- **Broker `mcp_sync`** queries MCP configs for a workspace by joining through `mcp_server_workspaces` instead of matching `mcp_servers.workspace_id` directly. Cache shape, sync cadence, and the workspace-facing API are unchanged.

### Removed

- **`agentcordon setup` subcommand.** Its broker auto-start behaviour moved into `agentcordon register --server-url`, so there is one registration path instead of two. Users on existing scripts should replace `agentcordon setup <url>` with `agentcordon init && agentcordon register --server-url <url>` (if keypairs are not yet generated) or `agentcordon register --server-url <url>` (if `init` has already run).
- Broken `GET /enroll.md` documentation pointer in the top-level README — the endpoint had no handler and always 404'd.
- Misleading copy on the MCP detail page that said "Workspaces owned by the same user as this MCP server automatically have access…". The Workspaces section on the detail page is now the sole source of truth for which workspaces are bound, and the same-owner Cedar policy (3a) only matches bindings that actually exist in the junction. Similar misleading copy on the MCP Permissions tab ("Default policies allow all enabled workspaces to access enabled MCP servers") is replaced with an accurate same-owner + bound description.

### Fixed

- **OAuth2 `client_credentials` proxy flow now correctly exchanges the client secret for an access token before injecting it into upstream requests.** Previously, the broker read `credential_type` from the ECIES envelope plaintext where the server never writes it, so every `oauth2_client_credentials` proxy call silently skipped the token exchange and injected the raw `client_secret` as a `Bearer` token. Against Microsoft Entra ID this manifested as `AADSTS700016` / `IDX14100: JWT is not well formed, there are no dots (.)`; other providers returned 401s with varying error text. The broker now reads `credential_type` from the outer `VendResponse` envelope where it is actually set. Verified live against Entra (`/v1.0/users`, `$batch`, cache hit and miss, error paths). Only `oauth2_client_credentials` credentials were affected — `oauth2_user_authorization`, `api_key`, and `bearer_token` flows were already correct. Any cached bearer tokens from before the fix are safely ignored because the broker now re-fetches on the correct code path. (`crates/broker/src/routes/proxy.rs`, `crates/broker/src/vend.rs`)

## [0.2.2] - 2026-04-08

### Fixed

- **OAuth2 refresh token rotation** — the broker now persists rotated refresh tokens back to the server when an upstream OAuth provider issues a new `refresh_token` on exchange. Previously, rotated tokens were discarded with a warning, which broke any RFC 6749 §6-compliant provider (Notion, Google, OAuth 2.1 implementations) after the first refresh: the cached access token would mask the problem for ~1 hour, then every subsequent call would return 401 until manual re-consent. The fix is atomic — if the server-side persistence call fails, the new access token is also not cached, preventing state divergence across broker restarts. (`crates/broker/src/oauth2_refresh.rs`, new server endpoint `POST /api/v1/workspaces/mcp/rotate-refresh-token`)
  - **Recovery note**: users currently locked out of a rotating provider must re-authorize the MCP server once through the admin UI. The fix cannot recover refresh tokens that have already been invalidated by the upstream.

- **MCP server template URLs refreshed** — verified all 12 remote MCP templates in `data/mcp-templates/` against current vendor documentation and updated endpoints that had migrated from SSE to streamable HTTP. Changed URLs: `asana` (`/sse` → `/v2/mcp`, deprecating 2026-05-11), `cloudflare` (`/sse` → `/mcp`), `intercom` (`/sse` → `/mcp`), `wix` (`/sse` → `/mcp`). Granola's `oauth2_resource_url` updated to include the `/mcp` path suffix to match its RFC 9728 protected-resource metadata. PayPal and Square kept on `/sse` since their vendor docs still publish that as canonical.

- **Release workflow publishes broker binary** — `build-broker` matrix added to `.github/workflows/release.yml`, mirroring the CLI's target set (5 targets including Windows). Previously, `/install.sh` served by the running server tried to download `agentcordon-broker-<target>` from GitHub releases and 404'd because no job was uploading it.

- **Linux binary glibc compatibility** — all three Rust build jobs (`build-gateway`, `build-broker`, `build-server`) now run on `ubuntu-22.04` (glibc 2.35) instead of `ubuntu-latest` (glibc 2.39).
